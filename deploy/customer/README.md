# Переносимый комплект организации

Профиль рассчитан на Linux с Docker Engine и Compose. Для установки не нужны исходники приложения, Node.js или окружение разработчика. Скопируйте этот каталог на сервер. Внешние 80/443 принадлежат Caddy; PostgreSQL, Redis, backend и frontend не публикуют свои порты на хост. HTTPS выпускается для домена, DNS которого указывает на сервер. Подсеть web `10.77.0.0/24` должна быть свободна; при изменении согласованно измените доверенные proxy CIDR backend.

Запустите `configure.py` с `--domain` и пятью аргументами образов `--backend`, `--frontend`, `--postgres`, `--redis`, `--caddy`. Каждый образ задаётся как `registry/name@sha256:<64 hex>`. Не используйте `main/latest`: комплект должен ссылаться на прошедшие CI совместимые версии. Программа создаёт `.env`, `runtime.env`, `database.env` с режимом 0600, новыми секретами БД/JWT/шифрования и отказывается перезаписывать их.

В `runtime.env` укажите согласованные SMTP и AI endpoints/credentials. Публичная регистрация закрыта по умолчанию. Для изолированного AI задайте `AI_LOCAL_ONLY=true` и явно настройте локальные providers, embeddings, изображения и OCR. Веса, GPU, контекст и ограничения должны соответствовать выбранному обслуживающему сервису; отсутствие внешнего fallback не означает, что модели уже доставлены на машину.

Проверка перед установкой: `docker compose --file compose.yml config --quiet`. Затем загрузите **именно перечисленные digest** и запустите `docker compose --file compose.yml up -d`. Миграции завершаются до API/workers. Проверьте `/api/readiness`, состояния контейнеров и `python -m scripts.operations_check` внутри backend. Первый именной оператор создаётся существующей командой `python -m scripts.platform_admin grant --email <адрес> --create --password-stdin` через stdin контейнера; пароль не передаётся в аргументах и не имеет значения по умолчанию. Участники получают персональные приглашения.

Постоянные данные: том `db`, `uploads`, `redis`, состояния Caddy; секреты конфигурации входят в отдельную зашифрованную резервную копию. Не копируйте volumes поверх работающей БД. Полный dump PostgreSQL и immutable-файлы uploads восстанавливаются сначала в отдельное окружение. Сохраните предыдущий manifest образов и проверенную копию до обновления. При неуспехе миграции остановите выпуск: возврат образа сам по себе не отменяет схему или пользовательские изменения. Для несовместимого downgrade используйте восстановление в отдельную БД и переключение после проверки.

Ежедневные задачи: `scripts.legal_admin purge`, `scripts.purge_delivery_secrets`, `scripts.purge_auth_challenges`, отчёт `scripts.purge_ai_history` в режиме dry-run, полный backup и его внешняя копия. Внешнее хранение на втором собственном сервере допустимо как отдельный от основного хост, если согласованы размещение, права и независимый ключ. Не переносите корневой SSH-ключ приложения для этой цели. В `lernium-infra/ops` находятся зашифрованное резервирование, проверка восстановления, rclone offsite read-back verification и монитор свежести.

Двухэтапный вход настраивается самим пользователем в `/account?tab=security`. Сначала подтвердите текущий пароль, перенесите секрет в приложение TOTP (6 цифр, 30 секунд), подтвердите код и сохраните десять одноразовых резервных кодов отдельно от устройства. Секрет зашифрован `DATA_ENCRYPTION_KEY`; этот ключ необходимо сохранять вместе с защищённой конфигурацией для восстановления. Вход по паролю, OIDC и LTI требует тот же фактор после подключения. Смена пароля не отключает MFA. Старые сеансы завершаются при подключении/отключении. Одноразовая настройка действует 10 минут, проверка входа — 5 минут; после 10 неверных кодов доступ к проверке ограничивается на 15 минут, независимо от смены challenge.

По умолчанию `MFA_REQUIRED_FOR_OPERATORS=false`: установка не подключает фактор за владельца и не блокирует существующих операторов без их участия. После личной настройки и проверки резервного входа каждым именным оператором установите `MFA_REQUIRED_FOR_OPERATORS=true` и пересоздайте backend. Тогда оператор без MFA получает только путь к настройке профиля; все административные API требуют подтверждение не старше `MFA_STEP_UP_SECONDS=600` (допустимо 60–900). UI сохраняет открытую форму и просит повторить действие после подтверждения, без автоматического повтора записи. Отправленные в поддержку пароли/секреты/резервные коды не запрашиваются; автоматического сброса чужого второго фактора нет. При утрате и устройства, и всех резервных кодов требуется отдельная проверка личности и регламент восстановления владельцем установки.

AI retention не удаляет содержимое по умолчанию и не заменяет процедуру удаления персональных данных. Без параметров команда `docker compose --file compose.yml exec -T backend python -m scripts.purge_ai_history` только выводит план. Сроки `--history-days`, `--artifact-days`, `--draft-version-days` задаются отдельно согласно действующему договору/утверждённой политике; пропущенная категория сохраняется. Передайте её реальный идентификатор в `--policy-reference`, сохраните JSON плана вне контейнера и проверьте список объектов. Ни «90 дней», ни другая универсальная длительность не считается согласованной автоматически.

После проверки выполните **ту же команду с теми же сроками и policy-reference**, добавив `--execute --plan-digest DIGEST_ИЗ_ПРОВЕРЕННОГО_ПЛАНА`. План вычисляется повторно под блокировкой; если набор изменился, операция откажется и потребует новый dry-run. Не ставьте `--execute` в необслуживаемый cron с заранее сохранённым digest. Опубликованные версии, закреплённые исходники и изображения, назначения, оценки, текущие/возобновляемые задания и учёт расходов сохраняются. Старые checkpoints без доказанной связи с запуском не удаляются автоматически. Согласованное удаление организации и юридические ограничения выполняются отдельной процедурой.

Для offline-поставки заранее экспортируйте все перечисленные Docker images, модели, токенизаторы, OCR-пакеты и лицензии; запишите SHA-256 каждого файла и версии. Импортируйте пакет до отключения сети и проверьте manifest. Настройка Docker registry mirror не считается доказательством автономности. Приёмочный запуск с запретом egress должен отдельно пройти генерацию, поиск, чат, изображения и перезапуск. Этот каталог не содержит вымышленных весов, лицензий, договора с заказчиком или отчёта о ещё не выполненном GPU-тесте.

`offline_bundle.py` собирает и проверяет **предоставленные файлы**, ничего не скачивает. Спецификация JSON содержит `schema: 1`, `bundle_id` и `components`. У каждого компонента обязательны `id`, фактическая `version`, неповторяющиеся `roles`, список `files` с относительным `path` и заранее проверенным `sha256`, а также `license` с `path`, `sha256`, `identifier` и `redistribution_review` — ссылкой на реальную проверку условий распространения. Для архива образа нужны его `image_ref` вида `registry/name@sha256:…` и фактический `image_id` из `docker image inspect`; единственный файл получают через `docker save --output FILE PINNED_IMAGE`. Перечислите весь комплект: backend/frontend/postgres/redis/caddy, text_model/embedding_model/image_model, text_runtime/embedding_runtime/image_runtime, tokenizers, ocr_rus/ocr_eng, fonts, dependencies. Модельный компонент может содержать несколько shards и файлов конфигурации. Шрифты и зависимости тоже должны иметь свой инвентарь и условия использования.

Сборка: `python offline_bundle.py assemble --spec /path/to/spec.json --destination /path/to/new-bundle`. Каталог создаётся новым; каждый файл проверяется, копируется по SHA-256, затем проверяется весь manifest. Храните `manifest.sha256` также по независимому доверенному каналу. Проверка после переноса: `python offline_bundle.py verify --directory /path/to/bundle --manifest-sha256 TRUSTED_DIGEST`. Неполный комплект, несовпадающий checksum, ссылки вне каталога и лишние файлы приводят к отказу. Секреты `runtime.env` не входят в этот пакет.

Импорт образов — отдельное явное действие: `python offline_bundle.py import-images --directory /path/to/bundle --manifest-sha256 TRUSTED_DIGEST --compose-override /path/to/new-offline-images.json`. Команда вызывает `docker load`, сверяет image ID и создаёт Compose override с точными локальными ID и `pull_policy: never`; это предотвращает скрытую попытку pull после потери registry digest при docker save/load. При запуске передайте оба файла: `docker compose --file compose.yml --file /path/to/new-offline-images.json up -d`. Runtime-образы моделей импортируются и выводятся отдельно: их GPU, mounts, параметры контекста, модельные команды, локальный TLS и запрет egress оператор настраивает по согласованному профилю. Успешная проверка bytes не является доказательством лицензии, корректности inference или испытаний без внешней сети.

В этой разработке проверены структура Compose и повторный запуск безопасной конфигурации в временном каталоге Linux. Фактическая установка, обновление с данными, load/RPO/RTO и offline GPU-приёмка фиксируются отдельным отчётом для конкретного комплекта.
