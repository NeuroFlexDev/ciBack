# Интеграции, доставка и договорный доступ

Ознакомительный доступ остаётся бесплатным. Платное подключение организации создаётся оператором по индивидуальному договору: в интерфейсе не появляются вымышленные тарифы, автоматическое списание или активация по переходу браузера на страницу успешной оплаты. Это соответствует опубликованным условиям редакции 2026-10-21 в lernium-docs/legal/ru.

## API v1

Актуальный контракт генерируется работающим приложением: `GET /api/v1/openapi.json`. Все остальные методы `/api/v1` требуют `Authorization: Bearer lrn_…`. Ключ не подходит для входа человека и не превращается в JWT автора. Владелец создаёт, отзывает и атомарно ротирует ключи через `/api/integrations/keys`. Исходное значение возвращается один раз; в БД хранится SHA-256, префикс, срок и scopes. Ротация сразу отзывает старый ключ. Использование журналируется без секрета.

| Метод | Scope | Результат |
|---|---|---|
| GET `/api/v1/courses` | courses:read | Курсы организации, без содержания и ключей ответов |
| GET `/api/v1/members` | members:read | Именные участники своей организации |
| GET `/api/v1/assignments` | assignments:read | Назначения и текущий прогресс |
| GET `/api/v1/results` | results:read | Серверные итоговые баллы и шкала, без ответов участников |
| POST `/api/v1/assignments` | assignments:write | Назначение опубликованной версии |
| DELETE `/api/v1/assignments/{id}` | assignments:write | Отзыв назначения с сохранением истории |

Списки принимают `offset` от 0 и `limit` от 1 до 100. Ответ: `version`, `total`, `offset`, `limit`, `items`. Назначения и результаты дополнительно принимают `user_id`. Идентификаторы целочисленные, принадлежат конкретной установке.

Создание назначения: `{"course_version_id": 12, "user_id": 24, "external_id": "hr:onboarding:2026:24"}`. `external_id` неизменяем внутри организации. Повтор того же тела возвращает прежнее назначение с `created:false`; другое тело с тем же идентификатором — 409. Отзыв не удаляет попытки и результаты. Для повторного обучения используется новый `external_id` и явно выбранная версия.

Ошибки содержат `detail`; заголовок `X-Request-ID` помогает найти техническое событие. 401 — ключ недействителен/истёк; 403 — нет scope или доступа; 404 — объект не найден в доступной области; 409 — конфликт версии/идемпотентности/состояния; 422 — некорректный запрос; 429 — ограничение с `Retry-After`; 503 — временный отказ зависимости. Чтение можно повторять; запись повторяется только с прежним внешним идентификатором.

## Webhooks и почта

События записываются в одной транзакции с изменением предметной области. Отдельный процесс `python -m app.workers.outbox` доставляет их после commit. Отказы используют ограниченную экспоненциальную задержку; истёкшая lease забирается другим worker. При сбое после приёма удалённой стороной возможен повтор, поэтому принимающая сторона обязана хранить `X-Lernium-Event-ID` и не выполнять событие повторно.

Подпись `X-Lernium-Signature: t=<unix>,v1=<hex>` — HMAC-SHA256 от `<unix>.<исходные байты тела>`. Секрет выдаётся владельцу один раз. Получатель сверяет подпись постоянным по времени сравнением и свежесть `t` в согласованном окне. Набор событий: `course.published`, `assignment.created`, `assignment.revoked`, `submission.graded`, `invoice.paid`, `member.revoked`. Ответ 2xx подтверждает доставку; перенаправления не выполняются. HTTPS соединяется с проверенным IP с TLS-проверкой исходного hostname, без proxy environment и DNS rebinding.

SMTP требует `SMTP_HOST`, `SMTP_FROM` и `DATA_ENCRYPTION_KEY`; логин/пароль настраиваются по требованиям почтового сервера. STARTTLS по умолчанию включён. `DATA_ENCRYPTION_KEY` — отдельный Fernet-ключ, обязательный для шифрования очереди и integration secrets; хранится с окружением в шифрованной копии. Замена ключа без миграции ранее зашифрованных значений недопустима. Очередь восстановления RU/EN сохраняет сообщение при отказе SMTP, не выдаёт существование аккаунта, прекращает отправку после 30 минут и стирает токен из тела после доставки. Приглашение действует 7 дней. Стабильный Message-ID помогает почтовому серверу распознать повтор, но не является обещанием exactly-once доставки SMTP.

Ежедневно запускаются `python -m scripts.purge_delivery_secrets` и `python -m scripts.purge_ai_history`. Неудачные webhook-пакеты можно повторить в течение 30 дней; затем полезная нагрузка удаляется, технический статус сохраняется. В журнале нет адресов токенов, паролей, ключей и SMTP-диагностики с секретами.

## OIDC и LTI

OIDC использует authorization code + PKCE S256, одноразовые state/nonce и привязку к HttpOnly cookie браузера. Проверяются подпись RS256/ES256 по настроенному JWKS, issuer, audience, azp, срок, nonce. Существующий аккаунт не захватывается по совпавшей почте: он связывается только из действующего локального сеанса. Создание новых участников отдельно включается владельцем для списка подтверждённых email-доменов; новая роль — участник. Локальный вход и резервный владелец сохраняются.

Callback: `/api/auth/oidc/callback`; короткоживущий одноразовый код попадает во fragment `/auth#sso_code=…&sso_state=…`. UI обменивает его через POST `/api/auth/oidc/exchange` с HttpOnly cookie, получает обычный AuthResponse и очищает fragment. JWT никогда не передаётся в URL.

LTI 1.3 регистрирует issuer/client/deployment и ключ инструмента отдельно для каждой LMS. Resource link явно закреплён за опубликованной версией; роль из launch не выдаёт административные права. Субъект LMS связывается владельцем с существующим участником либо отдельно включённое создание выдаёт изолированный технический email, который не используется для захвата реального адреса. Запуск подписан и одноразовый; при запрете third-party cookies встраивания LMS нужно открывать инструмент отдельной вкладкой. AGS использует подписанный OAuth client assertion; итог передаётся с исходной шкалой и возрастающим timestamp через durable outbox. Устаревшая оценка не обгоняет более новую в нашей очереди; LMS также обязана соблюдать порядок timestamp по стандарту.

Нормативные источники: [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html), [LTI Assignment and Grade Services](https://www.imsglobal.org/spec/lti-ags/v2p0/). Поддержка протокола в коде не заменяет проверку настроек конкретной LMS/IdP.

## Договоры и подтверждение оплаты

Оператор заполняет срок, валюту, квоты и индивидуальные условия AI, продления, отмены, возвратов и хранения с основанием в аудите. Счёт создаётся с суммой в минимальных единицах валюты; повтор номера с другими данными отклоняется. Банковское подтверждение доступно только оператору с референсом платежа и основанием. Один референс не оплачивает два счёта. Истечение договора запрещает новые изменения учебных данных, сохраняя просмотр, выгрузку, вход и продление. Автоматического удаления результатов нет; самостоятельная процедура удаления согласуется отдельно.

ЮKassa необязательна для договорного сценария. Callback является сигналом: сервер повторно читает платёж из API магазина и сверяет status, paid, invoice/organization metadata, сумму, валюту и отсутствие test flag. Повтор уведомления безопасен. [Протокол уведомлений ЮKassa](https://yookassa.ru/developers/using-api/webhooks). Настройка магазина и кассовой схемы не считается выполненной наличием кода.

## Эксплуатация

`GET /api/admin/operations` доступен только оператору: БД/Redis, очередь, диск, отказы и измеренные токены/стоимость. `python -m scripts.operations_check` выдаёт только технические показатели и ненулевой exit code при отказе. Канал доставки сигнала ответственному настраивается в существующем мониторинге заказчика; данные SMTP не подменяются фиктивными.

Переносимый профиль находится в `deploy/customer`. Все образы фиксируются digest; БД/Redis не имеют опубликованных портов. Локальный AI и отключение egress проверяются отдельно с выбранными весами и фактическим GPU. Коммерческая приёмка, настоящая доставка почты и интеграционный тест с конкретным заказчиком отражаются отдельно от автоматических тестов протокола.
